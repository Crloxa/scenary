## 0. 为什么必须重做一轮

现有仓库已经证明“接口能跑、容器能起、冒烟脚本能绿”，但这只证明了底盘具备可执行性，不能证明它已经是可交付的社区产品。当前主要问题集中在四个层面：

1. **产品层**：页面更像功能样例，缺少统一的信息层级、内容浏览节奏、空态/错误态和移动端细节；首次访问者无法快速理解“看什么、为什么留下、如何发布”。
2. **交互层**：上传、刷新令牌、失败重试、路由切换等边界路径不完整，错误时会出现重复请求、孤儿媒体、空白页面或状态丢失。
3. **工程层**：黑盒脚本覆盖了主链路，但没有前端自动化测试、后端集成测试、CI 门禁和可恢复的异步失败状态；“通过一次”不等于“持续可维护”。
4. **运维与安全层**：配置、对象存储、消息失败、备份恢复和可观测性仍偏开发环境，尚未达到可长期运行的最低线。

本轮目标不是继续堆功能，而是先把现有功能做成一个可信、好用、可回归的产品。任何新增功能都必须服从本文件的质量门槛。

## 1. 基线与成功标准

### 1.1 已确认基线

以下事实来自当前代码和已有证据报告；编号用于任务追踪。子 agent 可以补充问题，但不得删除已确认问题，除非给出验证证据。

| 编号 | 层面 | 当前事实 | 影响 | 优先级 |
|---|---|---|---|---|
| FE-001 | 视觉 | 主要操作依赖 emoji、手写 SVG 和大量圆角胶囊，缺少统一图标、间距、层级和响应式规则 | 视觉不稳定，品牌感弱，桌面与移动端都显得像 demo | P1 |
| FE-002 | 交互 | 首页、个人页、详情页缺少完整的加载失败、重试、图片失效、网络离线和空态分层 | 用户遇到网络波动时只能看到空白或 toast | P1 |
| FE-003 | 可访问性 | 表单缺少显式 label/错误关联，部分按钮只有颜色或 emoji 区分，键盘焦点和语义状态不完整 | 键盘、读屏和低视力用户不可用 | P1 |
| FE-004 | 上传 | 选中的文件会并发启动，未按文档限制并发度；移除文件不释放 object URL，也不清理已创建的游离媒体 | 浏览器内存泄漏、服务端脏数据、弱网下请求洪峰 | P0 |
| FE-005 | 上传 | 轮询超时只有失败文案，无法可靠取消；组件卸载后异步任务仍可能回写状态 | 页面切换后出现竞态和无效请求 | P0 |
| FE-006 | 认证 | `request.js` 刷新失败后仍会重放原请求一次；令牌放在 localStorage，启动时没有 `/users/me` 校验/恢复策略 | 401 场景多一次错误请求，XSS 风险和过期态体验差 | P0 |
| FE-007 | 路由 | ProfileView 只在 setup 时读取一次 userId，复用组件切换 `/user/1` 到 `/user/2` 时可能展示旧数据 | 用户主页内容错位 | P0 |
| FE-008 | 测试 | 前端只有 `npm run build`，没有组件测试、API mock、浏览器回归或性能预算 | UI 改动很容易回归而无人发现 | P1 |
| BE-001 | 认证 | 注册先查后插，竞争注册撞唯一键时可能落入 500；限流键和登出撤销缺少集成测试 | 错误码不稳定，安全行为无法持续回归 | P0 |
| BE-002 | 媒体 | MinIO 写入、数据库插入、MQ 发布不是可恢复事务；任一步失败都会留下孤儿对象/`status=0` | 用户看到永久处理中，存储空间持续污染 | P0 |
| BE-003 | 媒体 | 消费者最终失败进入 DLQ，但没有把媒体置为 `status=2`，前端只能等待超时 | 失败状态不可观察、无法指导用户重试 | P0 |
| BE-004 | 媒体 | WebP 解码失败时复制原图作为缩略图，可能保留原图元数据，且宽高为空 | 隐私策略与缩略图契约不一致 | P1 |
| BE-005 | 笔记 | 发布接口没有幂等键；重复提交会创建重复笔记；绑定媒体的更新缺少结果数校验 | 双击/重试会产生脏内容或部分绑定 | P0 |
| BE-006 | 缓存 | Feed 首页命中 L1 仍需查询覆盖索引；缓存与 DB 的一致性没有并发集成测试 | 缓存收益有限，竞态难以证明 | P1 |
| BE-007 | 数据 | media order、状态、可见性等约束主要靠应用代码，数据库没有足够的唯一性/检查约束 | 异常写入后难以修复 | P1 |
| BE-008 | 可观测性 | 没有统一 traceId、结构化业务事件、指标和告警接入；MQ 失败主要靠人工看日志 | 定位慢，无法知道失败率和延迟 | P1 |
| BE-009 | 配置 | 开发配置含可运行的默认账号/密码；Compose 使用 `latest` 镜像且服务依赖不完整 | 环境漂移，误把开发配置带到生产 | P0 |
| BE-010 | 测试 | 后端只有纯逻辑 JUnit，Repository、Redis、RabbitMQ、MinIO 编排依赖脚本 | 关键故障只能在部署后发现 | P1 |
| OPS-001 | 发布 | 没有 CI 工作流、依赖审计、镜像扫描、回滚演练和备份恢复验收 | 每次修改都依赖手工记忆 | P1 |
| OPS-002 | 对象与隐私 | 公共桶同时暴露原图和缩略图，历史直链迁移没有自动化脚本 | 原图泄露面大，部署迁移成本高 | P0 |

### 1.2 P8 完成标准

P8 只有同时满足以下条件才能标记完成：

- P0 问题全部关闭，或在 CHANGELOG 中明确记录阻塞原因、替代方案和负责人。
- 首页、发布、详情、个人页在 390px、768px、1440px 三个宽度下通过浏览器剧本；无水平溢出、遮挡、控制台错误和未处理 Promise。
- 前端至少有组件/工具单元测试、API 层 mock 测试和一条完整浏览器回归；后端至少补齐认证、媒体失败、发布幂等和缓存一致性集成测试。
- 图片上传失败、MQ 最终失败、access 过期、网络断开、空数据五类场景均有可见状态和可恢复操作。
- `docker compose config --quiet`、后端测试、前端测试/build、浏览器回归和证据报告全部可重跑；若后续配置 lint，再将 lint 纳入同一门禁。
- 不新增未登记依赖；新增 API 先更新 02 契约，新增数据库字段先写 Flyway migration。

## 2. 执行方式与边界

### 2.1 任务状态

每个任务只能处于 `未开始 → 实现中 → 待验收 → 完成` 四种状态。实现 agent 不得自行把任务标记完成；必须提交：改动文件、验证命令、结果、已知边界和证据报告路径。

### 2.2 改动边界

- 前端任务优先限制在 `frontend/src`、`frontend/package.json`、测试目录和必要的 nginx 配置。
- 后端任务优先限制在对应业务包、Flyway migration、测试目录和配置模板。
- 不为“看起来更干净”重排目录，不升级 Spring Boot/Vue 等基线，不引入组件库；所有依赖变更先登记 [01 §3.1 延后安装清单](../01-技术栈与总体架构.md)。
- 不修改真实 `.env`，不把账号、密码、Token、Cookie 写入测试输出或文档。

### 2.3 建议分支与提交

实现 agent 使用 `codex/p8-*` 分支或当前工作树中的等价隔离方式，每个工作流保持原子提交：

```text
fix(frontend): 修复上传取消与失败恢复
fix(auth): 处理并发注册唯一键冲突
test(note): 增加发布幂等集成测试
docs(p8): 归档前端重构验收证据
```

## 4. 前端重构规范

### 4.1 页面信息架构

| 页面 | 首要任务 | 必须可见 | 必须处理的异常 |
|---|---|---|---|
| 首页 | 浏览并进入详情 | 页面标题、内容卡、作者、时间/地点、加载进度 | 首次加载失败、分页失败、无内容、图片失效、网络离线 |
| 登录/注册 | 建立身份 | 当前 Tab、字段标签、密码规则、提交状态 | 参数错误、账号已存在、登录锁、网络失败 |
| 发布 | 快速完成一次发布 | 选图入口、顺序、处理状态、标题/正文、可见性、提交状态 | 文件不支持、超限、上传失败、处理失败、离开页面、重复提交 |
| 详情 | 安静阅读 | 标题、作者、时间、地点、图片、正文、返回入口 | 404、图片失败、删除中、网络失败 |
| 个人页 | 识别作者与作品 | 头像、昵称、简介、作品数、网格 | 用户不存在、作品加载失败、头像失败、空作品 |

### 4.2 组件边界

新增组件只在以下边界内落盘，避免每个页面重新发明一套样式：

- `AppShell`：导航、主容器、全局 toast、全局错误边界。
- `AsyncState`：loading / empty / error / retry 四态。
- `ImageWithFallback`：占位、加载失败、尺寸预留、懒加载。
- `Button`、`TextField`、`Textarea`、`Dialog`：统一焦点、禁用、错误和键盘行为。
- `WaterfallGrid`、`UploadQueue`：只管理展示和状态，不直接写 API。

组件库若要引入，必须先更新 01 §3.1、说明 bundle 成本和替代方案；本轮默认使用现有 Vue + Tailwind。

### 4.3 上传状态机

```text
selected -> uploading -> processing -> ready
    |          |            |           |
    +-------> removed   failed <--------+
                         |
                       retry
```

要求：状态转换只能由一个 composable 管理；每个 item 有 AbortController、mediaId、错误码、开始时间和重试次数；组件销毁时取消请求并释放 URL；提交只读取 `ready` 项且幂等键固定。

## 5. 后端可靠性规范

### 5.1 媒体上传故障矩阵

| 故障点 | 用户可见状态 | 服务端动作 | 后台动作 |
|---|---|---|---|
| 魔数校验失败 | 立即提示格式错误 | 不写对象、不写行 | 无 |
| MinIO 成功、DB 失败 | 上传失败，可重试 | 尝试删除对象并记录 traceId | 定期扫描未知对象 |
| DB 成功、MQ 失败 | 处理中并显示稍后重试 | 写 outbox/重试标记，不假装完成 | 重发或置失败 |
| 消费者处理失败 | 处理失败，可重试 | 自动写 status=2、保存失败原因/时间 | DLQ 告警与人工重放 |
| 发布成功、删除失败 | 笔记仍可见 | 软删事务与缓存失效重试 | 对账脚本 |

### 5.2 事务和幂等要求

- 外部对象存储和消息队列不属于 MySQL 事务；必须使用补偿、outbox 或可重试状态，不得用“吞异常后返回成功”掩盖失败。
- `POST /notes` 使用客户端生成的幂等键（例如 UUID）时，服务端保存并唯一约束；不带键的旧客户端走兼容路径但要记录告警。
- 每个批量写操作校验影响行数；少一行就回滚并返回明确错误。
- 消费者按 `mediaId` 幂等，重复消息不能生成重复媒体行，也不能把已经删除的资源重新标记为完成。

## 7. 给实现 agent 的交接任务

实现 agent 收到本文件后按以下顺序工作：

1. 先复核 §1.1 的问题，补充遗漏并在回复中引用文件和行号；不要直接大范围改代码。
2. 先完成 P8-01 至 P8-07，再做 P8-08 至 P8-13；P0 未完成前不得开始新增社交功能。
3. 每完成一个任务，运行该任务的最小测试；一组任务完成后写阶段证据，不要把“本地看起来正常”当验收。
4. 遇到需要新增依赖、API 字段或数据库字段时，先暂停该任务，更新 01/02/CHANGELOG，再继续实现。
5. 交付内容必须包含：改动摘要、测试命令与结果、未覆盖边界、后续风险、建议的下一个任务编号。

## 8. 明确不在 P8 做的事

P8 不实现关注、点赞、评论、私信、搜索、视频、地图和 AI 审核；这些内容进入 [05 后续开发路线图](../05-后续开发路线图与实施手册.md)，并且必须在 P8 质量门槛通过后立项。
