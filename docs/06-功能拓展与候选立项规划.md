## 3. A 类 · 愿景落差（思绪.txt 承诺了但没做/没规划全）

### A1 修图与滤镜（F7）——建议最高优先，P16

- **现状证据**：§2.2。发布页是"选图即发布"，无任何编辑步骤。
- **方案（两步走，前端为主，零新后端依赖）**：
  - 第一步：发布页内嵌编辑步骤——裁剪（自由比例+预设）、旋转、滤镜（CSS filter 滤镜组，约 15~20 个预设，实时预览）。前端 canvas 产出最终图后再走既有上传管线，后端零改动。
  - 第二步（可选增强）：拼贴合成器——模板选择 + canvas 合成预览，产物仍是一张合成图上传；若未来要求服务端合成再评估图像库（01 §3.1 登记）。
- **模块化落点**：`frontend/src/utils/imageEditor.js`（纯函数 API：load→adjust→export）+ `components/NoteEditor.vue`（发布页步骤组件）；feature flag `VITE_ENABLE_EDITOR` 可整体摘除；滤镜预设表数据驱动，物种树等后续功能不依赖它。
- **规模**：M（编辑器 3~4 天 + 回归 1 天）；**风险低**——不触后端契约，产物即普通图片。

### A2 AI 人物检测安全门（F4 → P13）——建议"规则先行"分段落地

- **现状证据**：P13 草案在 05 §8（状态模型/处理链路/管理审计三节齐备），MQ 消费者链路接缝已在（thumbnail / video.transcode 两个独立队列）。当前评论侧已有基础敏感词，图片侧无任何内容安全手段。
- **分段建议**：
  - 第一段（零 ML 成本，可与 P17 举报联动）：发布频率异常检测、文件哈希黑名单、图片侧敏感词（OCR 可选）、举报驱动人工下架——先有"处置闭环"再谈"自动识别"。
  - 第二段（重新立项时）：可插拔 person-detector consumer——自托管 YOLO/CLIP 微服务（或云 API），按 E3 的 provider SPI 模式做门面：超时（如 2s）、失败放行或转人工、成本上限、阈值+申诉而非硬拒（pixelfed 评估文档 §三-F4 的两条现实问题仍然成立）。
- **模块化落点**：C1 媒体管线 SPI（见 §5）是它的前置工程。
- **规模**：第一段 S~M；第二段 L（1~2 周含模型选型压测）。**依赖**：建议 E3/E4 完成后再评估，避免签名语义、地点语义两个变更面叠加。

### A3 生物物种树（方向二）——三期候选，模块接缝干净

- **现状证据**：README 演进路径已列三期；可行性评估（`../docs/pixelfed/02-思绪Scenary改造可行性评估.md` §四）已给出 B1~B3 拆解。代码中零占用。
- **方案骨架**（照搬评估结论并适配现有架构）：
  - `species` 新包 + `species` 表（parent_id 分类树、学名/俗名、来源=GBIF/用户贡献）+ `note_species` 多对多；
  - `SpeciesService` 门面对接 GBIF API，本地缓存表兜底外网抖动（坐标不出内网的隐私纪律同样适用于此：调 GBIF 查询的是物种名，不涉隐私）；
  - 发帖步骤加"识别/添加物种"（起步手动搜）；检索复用 P11 骨架（受控 LIKE + 游标），物种/地区两个维度加接口。
- **依赖与顺序**：依赖坐标能力（E3/E4）与标签经验（B5 的检索模式可复用）；**规模 L，建议拆 3 个增强包**重新立项。

### A4 全局地图浏览页——E4 之外的真增量，建议 E5

- **现状证据**：05 §6.6 的 E4 边界明确为"发布页选点 + 详情页小地图"，**不含**"以地图视角浏览全站/某人/某物种的笔记"。
- **方案**：新增 `/map` 路由——Leaflet 视野框查询 `GET /places/notes?minLat&maxLat&minLng&maxLng&cursor=`，聚合已公开且带坐标的笔记卡片；详情页小地图点击可跳转地图页并定位。后端只加一个只读接口 + 复合索引（latitude/longitude 已在 V7）。
- **边界**：不做路线/导航/附近的人/地理围栏（延续 E4 边界）；瓦片源与离线降级策略继承 E4。
- **规模**：M；**依赖**：E4 完成（复用其地图组件与 flag 机制）。

## 5. C 类 · 工程模块化（为三期演进预留的接缝）

| # | 模块化项 | 内容与动机 | 前置关系 |
|---|---|---|---|
| C1 | **媒体处理管线 SPI** | 现状是 ThumbnailConsumer / VideoTranscodeConsumer 两个独立消费者。抽象为有序 consumer 链（元数据→缩略图→[审核]→[水印]…），每环可独立开关/降级/进 DLQ。是 A2 第二段、水印、病毒扫描等一切"媒体后处理"的公共底座 | P13 立项前置 |
| C2 | **领域事件 + Outbox** | P10 选择同步通知是正确的阶段性决策；但 feed/notification/search 三个模块各自读库的耦合面会随功能增长。按 05 §2.2 既有事件规则引入 `note.published/updated/deleted` 等领域事件 + outbox 表（同事务写、后台投递），消费方按 routing key 订阅 | P14 拆分（worker→search→notification）的技术前置 |
| C3 | **独立 worker 进程** | 转码/审核是 CPU 大户，与 Web 进程同容器会互相挤占（P8 已有 ffmpeg 资源竞争记录）。拆法简单：同一 jar 以 `--spring.profiles.active=worker` 起消费者实例、关 web 端口，Compose 加一个 service | P14 §9.2 拆分顺序第一步，可独立先行 |
| C4 | **可观测性最小集** | P14 §9.3 已定义最小指标清单（请求量/错误率/p95、登录失败率、上传成功率、媒体处理延迟、DLQ 深度、缓存命中率、连接池）。不必等规模化：actuator/micrometer 暴露 `/actuator/prometheus` + compose 加 Prometheus/Grafana 两个容器 + DLQ 告警阈值进 ops 脚本。traceId 结构化日志已在 | 独立可做；注意这是"运行时功能"而非线上部署方案，但涉及 compose 增容器，需登记 |
| C5 | **OpenAPI 文档** | springdoc 一行依赖 + 按需注解，与手写 02 契约并存（01 §3.1 已登记"低代价"行）。收益：前端联调与回归工具不再靠手写 .http | 随时 |
| C6 | 前端 TS 化 | 01 §3.2 列为后续增强。建议不单独立项，随新视图逐步迁移（`allowJs` 共存） | 顺手做 |
