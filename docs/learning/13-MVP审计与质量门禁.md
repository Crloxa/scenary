# 13 · MVP 审计与质量门禁

> 触发：MVP 复验后进行前后端代码审计，并把问题拆成 P8 改进任务。主题不是“如何把脚本跑绿”，而是“如何证明一个主链路真的可交付”。

## 现象

Scenary 的 API 黑盒脚本、前端构建和 Compose 冒烟都曾经通过，但继续审计时仍发现多类高风险问题：

- Vue Router 复用同一组件时，`/user/1` 跳到 `/user/2` 可能继续显示旧资料；
- 前端登出只清本地存储，没有调用后端撤销 refresh token；
- 公开端点的可选 token 解析不检查 access 黑名单，登出后的 token 仍可能被当作“本人”；
- 发布笔记先检查媒体再绑定，两个并发请求可能争抢同一媒体；
- refresh 旋转把白名单检查和删除拆成两个 Redis 操作，并发重放可能签发两对令牌；
- MQ 发布失败或消费者最终失败时，媒体可能长期停在 `status=0`，而前端只会等轮询超时；
- 首页请求失败被渲染成“还没有风景”，用户无法区分故障和真实空数据。

这些问题都不会被一条“注册→上传→发布→浏览”的顺序 happy path 稳定捕获。

## 原因

原有验收主要验证“功能是否存在”，没有把以下维度设成独立门槛：

1. **状态转换**：请求成功、失败、取消、超时、重试、组件卸载后的状态是否仍然闭合。
2. **并发与重放**：同一资源被同时写入、同一令牌被同时刷新、按钮被重复点击时，结果是否仍然唯一。
3. **权限生命周期**：登录、登出、禁用、私密可见性和可选身份解析是否使用同一套撤销语义。
4. **外部系统故障**：MySQL、Redis、RabbitMQ、MinIO 任一暂时不可用时，是否留下孤儿对象、半成品行或永久处理中状态。
5. **用户可理解性**：错误、空数据、加载中和资源不存在是否有不同的界面状态。

另外，黑盒脚本依赖已有数据和容器状态，容易只证明“这一次能跑”。没有代码级边界测试、干净环境和失败注入，绿色结果的外推范围就会被高估。

## 原理

交付质量应按“路径 × 状态 × 视角”拆开，而不是只按接口数量统计：

```text
一条用户路径
  × 正常 / 失败 / 取消 / 超时 / 重试
  × 匿名 / 本人 / 他人 / 已撤销凭证
  × 单请求 / 重复请求 / 并发请求
  = 可交付验收矩阵
```

对 Scenary 来说，几个可复用的判断规则是：

- **外部副作用不能假装属于数据库事务**。对象存储和消息队列写入失败时，必须有补偿、outbox、重试或终态记录；吞掉异常只会把故障推迟到用户轮询。
- **检查后再更新不是并发安全**。资源所有权、`note_id IS NULL`、refresh 白名单等条件必须放进原子更新/脚本/锁，并检查受影响行数。
- **缓存一致性要先定义正确性，再谈命中率**。版本化 key、提交后失效、作者资料变更失效和缓存降级都要有明确语义，不能用每次回表掩盖设计不清。
- **匿名解析也属于认证边界**。公开接口“带 token 则增强”时，黑名单、过期、账号禁用和非法 claims 仍必须有统一策略。
- **UI 的空态不是错误态**。只有请求成功且结果为空时才能显示空态；网络错误必须保留错误上下文和重试入口。
- **证据报告是状态机的一部分**。Checklist 只记录状态，报告必须记录命令、环境、结果和未覆盖边界；缺一项就不能把阶段标为完成。

## 我怎么验证的

1. 阅读 `AGENTS.md`、`docs/01`、`docs/02`、`docs/03`、`docs/HANDOVER.md`，先确认项目契约、阶段边界和现有证据，而不是直接凭页面观感改代码。
2. 对前端视图、请求层和路由逐文件检查，复现了两个具体现象：
   - 后端未启动时，首页同时出现 502 toast 和“还没有风景”；
   - 320px 视口下，顶部“发布”和“登录/注册”按钮发生文字折行。
3. 对后端认证、媒体、笔记、缓存和消费者代码做竞态与失败路径推演，重点查找“先查后写”“吞异常”“事务外副作用”“可选 token”四类模式，并将结果编号为 `FE-*`、`BE-*`、`OPS-*`。
4. 把审计结论落到 [前端审计报告](../frontend-audit-2026-09-02.md) 和 [04 产品与工程改进总纲](../04-产品与工程改进总纲.md)，为每个 P0/P1 问题补文件边界、验收条件和证据要求。
5. 前端首批止血完成后运行 `cd frontend && npm run build`，结果为 PASS；同时运行 `git diff --check`，确认当前改动没有空白错误。后端 P0 尚未实现，因此没有把 P8 Checklist 勾选为完成。

## 可复用结论

- 一个“能跑”的 MVP 只能说明主链路存在；要称为可交付 MVP，至少还要证明失败可恢复、并发不破坏数据、凭证可撤销、错误可理解、证据可重跑。
- 审计报告应同时给出**现象、代码位置、复现方式、影响、修复方向和验收标准**。只写“建议优化”无法指导 agent，也无法在下一轮判断是否真的修好。
- 先做 P0 正确性和安全止血，再做视觉和新功能。否则新功能会建立在错误的身份、媒体和缓存语义上，返工范围更大。
- 每个阶段都要保留未覆盖边界。没有测试过的并发、故障注入、移动端和无障碍场景，必须明确写成风险，而不是默认通过。
