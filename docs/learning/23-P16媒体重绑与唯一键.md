# 23 · P16 笔记编辑：媒体重绑与唯一键的两次撞墙

> 2026-09-19 · P16-01 笔记编辑施工中踩坑，亲测可复现。

## 现象

编辑接口 PUT /notes/{id} 在"替换媒体集合"场景 50000，但返回 50000 的那次请求**部分生效**与否取决于撞哪张表：
1. 第一次：`SQLIntegrityConstraintViolationException: Column 'order_no' cannot be null`——解绑旧媒体 `SET order_no = NULL` 直接炸。
2. 修掉后换"重绑新集合"路径：`Duplicate entry '261-1' for key 'media.uk_media_note_order'`——给新图绑 order_no=1 时，旧图还占着 (note, 1)。

## 原因

两张表约束在发布链路里"永远正确"，因为发布只有 INSERT 路径：
- `media.order_no` 是 NOT NULL 列（V1 建，游离媒体无语义值可填）；
- `uk_media_note_order (note_id, order_no)` 唯一键假设绑定操作单调递增——发布从空集开始，编辑是"原位改写"，中间态必然撞键。

## 原理

唯一键冲突的本质是**在同一个键空间里做原地交换**：旧值 (note,1) 未让出之前，新值 (note,1) 写不进去。正确顺序是先把整个键空间清空（全解绑），再按新集合写入。这也是"全量替换"语义下唯一安全的写序——增量式"先加后删"在唯一键下不可行。

## 我怎么验证的

1. `docker compose logs backend | grep -A3 "unhandled exception"` 拿到两段完整 SQL 与约束名；
2. 修复一：`unbindFromNoteExcept` 改 `SET order_no = 0`（0 = 游离标记，读路径只按 note_id 过滤不受影响）；
3. 修复二：`NoteService.update` 改为 `unbindFromNoteExcept(noteId, List.of())` 全解绑后再循环 `rebindToNote(noteId, i+1, id)`；
4. 黑盒 `test-p16-gap.mjs` 断言：替换后旧媒体 `note_id IS NULL AND order_no=0`、再编辑可把游离媒体重新加入且顺序正确，20/20 全绿。

## 可复用结论

- 给已有唯一键约束的表做"集合替换"，先清空再写入是唯一安全顺序；设计新表时若字段 NOT NULL 且语义上"无值"，用哨兵值（0/空串）而不是 NULL，并为哨兵值写进表注释。
- 建表时的 CHECK/NOT NULL/UNIQUE 约束在首条写入路径上都是隐形的，新增第二条写路径（编辑/迁移/修复脚本）前，先枚举所有约束对中间态的判定。
- 单测 mock 掉了真实 SQL，这类约束冲突只在黑盒/集成层暴露——黑盒必须覆盖"改写"而不只是"创建"。
