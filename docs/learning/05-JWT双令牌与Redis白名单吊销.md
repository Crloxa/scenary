# 05 · JWT 双令牌与 Redis 白名单吊销

> 触发：首次实现完整认证域（Phase 3-3.4），backlog L1 到点。所有结论均由 `docs/dev/test-auth34.mjs` 的实跑结果支撑（PASS=18）。

## 现象

一开始直觉上是矛盾体：access token 号称"无状态"，refresh 却要在 Redis 里存一条 `auth:refresh:{userId}:{jti}` 才算数；登出更是双管齐下——白名单全删 + 把当前 access 的 jti 写进黑名单等它自然过期。为什么不能只做一种机制？

## 原因

两种令牌的生命周期诉求完全相反：

| | access | refresh |
|---|---|---|
| 存活期 | 2 小时 | 30 天 |
| 出现频率 | 每个请求一次 | 几天一次 |
| 校验成本要求 | 必须 O(1) 且不打存储（QPS 大头在这） | 可以付出一次 Redis 读 |

给 access 也做服务端状态校验，等于每个 API 都多一跳 Redis——JWT"免查库"的红利归零；完全不管理 refresh，则一个 30 天长效凭证泄露后无法追回。

## 原理（本项目的取舍）

1. **白名单而非黑名单管 refresh**：信任半径小的令牌用"在场名单"表达（默认拒绝），泄露后删除名单项即吊销。
2. **旋转（rotation）防重放**：每次 refresh 删旧 jti、签发全新一对。被偷走的旧 RT 与合法客户端竞速时几乎必输——先到者得新令牌，后者拿旧 RT 刷新立刻 40101，反而暴露了盗用事实。实测：同一路径第二次刷新返回 `40101`（test ⑦）。
3. **access 黑名单是"残局收拾"不是主防线**：登出后剩余寿命 ≤2h 的 access 在拦截器查黑名单 key（`auth:access:bl:{jti}`，TTL=自然过期时刻），过期后键自动消失，不产生垃圾数据。
4. **登录锁与计数器共用 Redis 形态**：`rl:loginfail:{username}:{ip}` INCR+首刷置 900s TTL，满 5 转 `rl:loginlock:*` 锁定并删计数器重启循环。实测第 5 次起连正确密码也返回 42001 并带剩余秒数。

## 我怎么验证的

`docs/dev/test-auth34.mjs`（Node fetch 直驱）关键断言：

```
PASS | 首次刷新 code=0 且新令牌不同
PASS | 旧 refreshToken 重放 code=40101
PASS | 登出 code=0
PASS | 登出后刷新 code=40101(白名单已吊销)
PASS | 第5次错密触发42001 | 登录失败次数过多，请 900 秒后再试
```

另可用 redis-cli 直接观察：登录一次后 `KEYS auth:refresh:*` 恰一条，刷新后该 jti 键消失、出现新 jti 键。

## 可复用结论

1. "无状态 JWT"宣传的是**传输凭证**无状态，认证体系整体仍需一处有状态存储来获得可撤销性——这个存储的读写频率应该与令牌使用频率成反比。
2. 任何长期凭证的接口都要假设"终会被偷"，设计目标是限制其当量（短 TTL+单次有效）而不是幻想永不泄露。
3. 契约没有的语义别乱发明错误码：密码错误不是"token 无效(40101)"也不是"未登录(40100)"，本项目落位 40000+统一文案（记于 CHANGELOG v1.9）。
