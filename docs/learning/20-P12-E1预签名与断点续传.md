# 20 · P12-E1 预签名与断点续传

> 触发：完成 P12-E1，并在真实 Compose/MinIO 环境验证分片直传、刷新恢复、服务端合并和过期清理边界。

## 现象

大视频若一直经后端 multipart 代理，上传请求会长期占用后端连接和请求体缓冲；网络中断后只能从头上传。P12 基础链路虽然已能上传和转码，但还没有会话级的恢复入口。

## 原因

上传动作同时包含浏览器传输、对象存储写入和媒体入队三个生命周期。把它们绑定为一个请求，会让浏览器无法知道哪些字节已经落盘，也无法在刷新后安全恢复。另一方面，若只相信前端记录的片号，恶意或损坏分片可能在合并时绕过大小和格式校验。

## 原理

服务端先创建带 owner、声明总大小、总片数和过期时间的会话，为每个片号分配带会话 UUID 前缀的对象 key。浏览器从服务端取得短时 PUT 预签名 URL，直接把 8MiB 分片写入 MinIO；服务端的 GET 会话接口再以对象实际大小重建已上传分片视图。

complete 不是“收到片号就成功”：服务端抢占会话进入合并态，逐片 stat 实际大小，校验前片固定 8MiB、末片期望大小和总大小，再重新嗅探首片魔数，最后用 MinIO compose/copy 生成原始媒体并投递既有视频转码队列。完成状态保存 `mediaId`，重复 complete 直接返回同一媒体。会话元数据和分片对象由过期/取消清理；浏览器只保存文件指纹、会话信息和已完成片号，不保存文件内容。

## 可复用结论

- 预签名 URL 只能授权到服务端已登记的会话对象 key；前端保存的片号是优化信息，合并时必须以对象存储实际大小为准。
- complete 要有数据库状态抢占和已完成媒体 ID，才能同时防并发重复合并、支持幂等重试并让分片清理有明确时机。
- 断点恢复应持久化“文件指纹 + 会话元数据 + 已完成片号”，重新选择文件后再由服务端核对对象状态；不要把大文件内容塞进 localStorage。
- 过期、取消、合并失败都要定义对象和数据库记录的清理边界；清理失败应可观测并允许后续任务重试，不能把异常静默当作成功。
