# 19 · P12 视频转码与地点隐私

> 触发：完成 P12 视频与地点基础链路，并在真实 Compose 环境发现并修复 480p 等比缩放产生奇数宽度导致 libx264 失败的问题。

## 现象

视频上传接口能返回 `PROCESSING`，但一条 640×360 的 16:9 夹具在容器中进入 `FAILED`，视频 DLQ 出现一条失败消息；封面步骤和 720p 转码本身没有失败。

## 原因

480p 目标滤镜写成 `scale=854:480:force_original_aspect_ratio=decrease` 后，ffmpeg 按原始比例得到 853×480。H.264 编码器要求宽高通常为偶数，libx264 因奇数宽度拒绝打开编码器，进程退出码为 187。

地点链路的另一个风险是把 EXIF GPS 当作公开地点直接返回。EXIF 只能作为服务端候选值；只有用户明确选择分享坐标时，公开详情才可以返回经纬度。

## 原理

转码器先用 ffprobe 读取视频流宽高和时长，再用 ffmpeg 参数列表生成封面、720p 和 480p 产物。保持比例的 `scale` 可能产生奇数尺寸，因此在视频编码滤镜后追加 `pad=ceil(iw/2)*2:ceil(ih/2)*2`，把单边向上补到最近偶数，不改变画面比例。消费者失败时先写入视频失败状态，再 `nack(requeue=false)` 进入视频专用 DLQ，图片缩略图队列不共享毒消息。

EXIF 读取只保留候选经纬度到服务端字段；发布服务按 `MAP`、`MANUAL`、`EXIF` 区分来源，详情响应对 `EXIF` 来源清空坐标。原始视频对象 key 只在服务端实体和转码读取链路中使用，媒体响应只返回封面与转码播放地址。

## 我怎么验证的

1. 第一次运行 `node docs/dev/test-p12-video-location.mjs` 得到魔数/处理中/原始路径 3 项通过，转码失败；读取容器日志和失败行确认 `video tool failed exit=187`。
2. 在容器中用同一 640×360 夹具复现 `853,480` 失败，再增加偶数 `pad` 后得到 `854,480`，退出码为 0。
3. 重建 Compose 后再次运行黑盒脚本，得到 `PASS=11 FAIL=0`：封面 JPEG、720p/480p MP4、MAP 坐标、EXIF 坐标隐藏、V7 字段和四条队列均通过。
4. 运行 `docker compose exec -T backend wget -qO- http://localhost:8080/actuator/health` 得到 `{"status":"UP"}`；容器内 `ffmpeg/ffprobe -version` 均为 8.1.2；后端 JUnit `39/39`、前端 Vitest `31/31`、三浏览器 Playwright `3/3`。

## 可复用结论

- 视频编码前不要只验证“目标宽高”，必须验证保持比例后的实际尺寸；对 H.264 输出统一保证偶数宽高。
- ffmpeg 通过 `ProcessBuilder` 参数列表调用，失败状态、日志和 DLQ 要形成同一条可追踪链路；不要把异常视频 requeue 成无限重试。
- EXIF 是隐私敏感的候选元数据，读取和公开分享必须拆成两个明确步骤；公开响应应按来源做最后一道清洗。
- 阶段验收要同时覆盖主机单测、容器工具链、真实对象存储产物和浏览器状态；只测 API 包络不能证明转码产物可播放。
