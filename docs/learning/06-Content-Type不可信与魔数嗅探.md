# 06 · Content-Type 是自报家门：上传必须嗅探魔数

> 触发：首次实现文件上传管线（Phase 3-3.6），附对实 spoof 用例证据。

## 现象

表单里同时给两张"jpg"：一张是真 PNG 把扩展名改成 `.jpg` 并把 HTTP 头 `Content-Type` 标成 `image/jpeg`；另一张干脆是纯文本。直觉上"校验一下请求头里的 MIME 就够了"，但两者必须都被拒绝——否则马脚全开：*.svg 内嵌脚本、伪装成图的可执行体、后续消费者解码崩溃等都从这里进来。

## 原因

HTTP 头的 `Content-Type` 是**发送方自我声明**，浏览器只按它决定"怎么展示"，服务器从来不验证它与字节流的关系。multipart 场景更糟：每个 part 的 content-type 同样是客户端说了算。唯一可信的是**字节序列本身**：

| 类型 | 文件头特征 |
|---|---|
| JPEG | `FF D8 FF` |
| PNG | `89 50 4E 47` |
| WEBP | 字节 0..3=`RIFF` 且 8..11=`WEBP`（注意跳过 4 字节长度域）|
| GIF | `GIF87a` / `GIF89a` |

## 我怎么验证的

`docs/dev/test-media36.mjs`：

```
PASS | 内容伪装 -> 40000 | 仅支持 jpeg/png/webp/gif 图片，且文件内容须与扩展名一致
```

该用例的构造就是"文本字节 + 客户端声明 image/jpeg"，命中的正是上面结论。反向对照：纯节点 zlib 手工拼装的合法 PNG（仅 69 字节）直接通过全部管线并成功匿名回读——证明白名单放行的依据确实是魔数而非其他巧合。

## 可复用结论

1. 上传白名单只认**读出来的文件头**，客户端任何 header 仅当提示。
2. 嗅探只需头部十几个字节：Java 侧用 `mark()/reset()` 包装流即可读完再透传原始流给对象存储，不必整文件进内存。
3. 一张手工编码的最小合法 PNG 是图形管线的最好测试夹具：体积极小、可精确断言、且天然供下游真实解码器消费（本项目缩略图消费者将复用它）。
