# 14 · P8 验收证据与异步状态

> 触发：P8 全量验收完成，并处理了“异步媒体状态、持久化测试数据、上下文中断后重复执行”三类容易混淆的证据问题。

## 现象

P8 的改动覆盖前端请求层、图片上传、RabbitMQ 缩略图、笔记发布、数据库 migration、Compose 和运维脚本。单看某个接口或某次页面操作，容易把“请求返回成功”误认为“异步链路已完成”，也容易把上一次中间 checkpoint 的 13/29 等旧数字继续写进当前交接文档。

本轮还遇到两个实际信号：后端测试在 Windows 本机曾受编译器/控制台环境干扰，Docker Maven 测试首次运行需要下载完整依赖；缩略图最终失败则必须先把 media 写成失败终态，再确认消息进入 DLQ。

## 原因

异步系统的结果不是一个 HTTP 返回值，而是多个状态的组合：数据库状态、对象是否存在、消息是否进入 DLQ、前端是否停止轮询。持久化 Compose 卷又会保留前一次测试的计数和数据，因此“脚本能否再次运行”与“脚本断言是否正确”是两个问题。

如果只在聊天上下文里记录“已经通过”，上下文压缩后就会丢失命令、退出码、环境和边界，下一次接手者只能重复跑可能产生副作用的测试。

## 原理

可复现验收至少要固定四个维度：

```text
实现版本 + 运行环境 + 命令退出码 + 断言/状态结果
```

对异步媒体流程，正确的验收顺序是：

```text
发布消息 → 等待数据库终态 → 检查失败原因/时间 → 检查 DLQ 增量 → 清理夹具
```

其中 `status=2` 是用户和后台都能理解的失败终态，DLQ 是消息层的补偿证据；两者缺一都不能证明“失败可观察”。对缓存并发则要同时检查所有请求成功和版本化缓存键存在，不能只看一次响应。

## 可复用结论

- 每个 checkpoint 都要立刻写回 `evidence`、`HANDOVER` 和 `CHANGELOG`；文档是跨上下文的持久化状态，不是测试结束后的可选总结。
- 异步故障要断言“业务失败终态 + 消息补偿位置”，并清理临时消息/对象；只看到日志或只看到 DLQ 都不够。
- 持久化测试环境中，测试脚本必须随机化用户、按增量检查队列，并把可清理资源写进脚本；否则第二次运行会把环境噪声误判成回归。
- 当本机工具链不稳定时，可以固定版本的 Docker 工具容器和 named cache 取得可复跑证据，但要把镜像摘要、挂载路径、命令和退出码一起记录。
- 浏览器人工剧本与代码级测试互补：前者证明真实页面和用户可见状态，后者证明刷新、上传和组件边界；两者不能互相替代。
