# 15 · P9 社交关系表与幂等写入

> 触发：完成 P9 社交最小闭环，并首次把点赞、收藏、关注三类关系以数据库唯一键作为并发幂等边界。

## 现象

P9 需要让用户对公开笔记点赞、收藏以及关注作者，同时支持刷新后恢复状态。多个请求可能同时写同一条关系；如果只在 Java 中先查再插入，20 个并发请求可能产生重复关系或计数漂移。首页 Feed 还会复用卡片缓存，不能把用户私有状态直接写进共享缓存。

## 原因

关系的真实事实是“某用户与某笔记/用户是否存在一条边”，不是一次请求是否执行过。并发请求之间的先查结果可能相同，因此必须由数据库唯一键完成最终去重；展示状态和计数则应从关系表重新聚合。共享 Feed 卡片只保存公共卡片字段，登录视角的 `social` 状态在返回前按 viewer 批量补齐。

## 原理

P9 使用三张关系表：`note_likes(note_id,user_id)`、`note_bookmarks(note_id,user_id)`、`follows(follower_id,following_id)`。三组业务键分别设置唯一索引，写入使用 `INSERT IGNORE`，取消使用无条件 `DELETE`，因此重复 PUT/DELETE 都满足幂等契约。社交写事务先通过 note/user Service 门面锁定并校验目标，再写关系，最后聚合返回当前状态；自关注同时由服务校验和数据库 CHECK 约束兜底。

匿名详情只返回公开计数和全 false 的私有状态；收藏列表通过 `bookmark.id` 游标倒序，并过滤已删除或不公开笔记。Feed L1 缓存不包含用户状态，命中后按当前 viewer 重新 enrich。

## 我怎么验证的

1. 启动 Compose 后检查日志：Flyway 校验 4 个 migration，当前 schema 版本为 4。
2. 执行 `node docs/dev/test-p9-social.mjs`，得到 `PASS=13 FAIL=0`；脚本覆盖匿名详情、20 次并发点赞/关注、重复取消、重复收藏、收藏游标、自己关注自己、私密/删除笔记和禁用用户边界。
3. 黑盒脚本对点赞关系执行数据库实查，20 个并发 PUT 最终 `COUNT(*)=1`，详情聚合 `likeCount=1`；关注关系同样实查为一条且主页 followerCount=1。
4. 执行 Docker Maven 测试得到 `26/26`，其中 `SocialServiceTest` 5 项覆盖服务编排和收藏游标；执行前端 `npm test` 得到 `15/15`，构建得到 `101 modules transformed`。
5. 浏览器只读访问首页、`/note/130` 和 `/bookmarks`，确认卡片/详情具有明确的点赞收藏无障碍名称，收藏路由可达。真实写入由黑盒和组件测试完成，避免污染浏览器验收数据。

## 可复用结论

- 关系型社交动作优先把“唯一业务边”建成唯一键，服务层只负责权限和目标状态，数据库负责并发去重。
- 共享列表缓存不要缓存 viewer 私有状态；公共卡片命中后按 viewer 批量补齐，既保持缓存复用又避免串用户状态。
- 幂等取消的正确验收不是“没有报错”，还要同时检查关系表已归零、聚合计数归零以及刷新后的列表/详情状态。
- P9 的关注、评论、通知并非同一复杂度：关系事实可以先同步落库；事件通知和频率限制留给 P10，并在引入队列前单独定义失败补偿证据。
