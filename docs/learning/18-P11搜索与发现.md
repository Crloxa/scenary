# 18 · P11 搜索与发现

> 触发：完成 P11 首期公开笔记搜索，并验证受控 LIKE、可见性过滤、opaque cursor、V6 索引和空库前向迁移。

## 现象

P11 需要同时支持中文、英文、地点和作者昵称搜索，还要保证私密、软删和禁用作者不泄露；如果直接拼接 LIKE，`%` 和 `_` 会变成通配符，分页也可能被不同查询或排序方式复用。

## 原因

当前数据量和查询样本不足以证明 Elasticsearch 的收益，而搜索结果的可见性状态会随软删和禁用实时变化。首期需要一个不加新依赖、权限边界清晰且能测出基线的实现。

## 原理

搜索词始终通过参数绑定，并额外转义反斜杠、`%`、`_`，让 LIKE 保持字面匹配。查询在 `notes` 和 `users` 上实时加入公开、未删除和正常作者条件；相关性用字段命中权重计算，最终追加时间和 id 稳定排序。opaque cursor 携带 query、sort 和上一条排序锚点，服务端拒绝跨查询或跨排序复用。V6 只补充可见性、时间、作者连接和媒体封面回表索引，不建立搜索副本。

## 我怎么验证的

1. 通过 `node docs/dev/test-p11-search.mjs` 验证标题、正文、地点、作者昵称、大小写、特殊字符、私密/软删/禁用作者过滤、recent/relevance 和 cursor，结果 `13/13`，20 次搜索样本 p95 `17.14ms`。
2. 通过 `pwsh -File ops/rebuild-search-index.ps1` 验证 `ANALYZE TABLE` 全部 OK，EXPLAIN 选择 `idx_search_visibility_created_id`。
3. 通过后端一次性容器指向临时空 schema，观察 Flyway 从 Empty Schema 应用 V1~V6；查询迁移历史确认 6 个版本成功、4 个搜索索引存在，随后删除临时 schema。
4. 通过 `cd backend && mvn -q test`、`cd frontend && npm test`、`npm run build` 和 P11 三浏览器 Playwright 专项，分别得到 `37/37`、`27/27`、`107 modules` 和 `3/3`。

## 可复用结论

- 没有真实查询样本和慢查询数据时，先用受控 LIKE 完成可用搜索，并把“何时升级搜索引擎”写成可验证的出口条件。
- 搜索的权限条件应在查询层实时执行；不要为了性能复用带有不同 viewer 或过期状态的 Feed 缓存。
- cursor 必须绑定 query、sort 和稳定排序锚点；只编码 id 而不绑定上下文，容易把另一种排序的游标误当成当前页坐标。
- Flyway 前向迁移既要在已有业务库验证，也要在隔离空 schema 验证；空库检查必须使用临时 schema，避免用 `down -v` 误删开发数据。
