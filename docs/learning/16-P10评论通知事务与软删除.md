# 16 · P10 评论通知事务与软删除

> 触发：完成 P10 评论与通知闭环，并首次在同一 MySQL 事务内写入评论事件和站内通知。

## 现象

P10 同时需要一级评论、回复、删除占位、评论限流和点赞/关注/评论通知。评论回复还必须禁止跨笔记引用；通知查询要支持倒序游标和未读数，删除评论后通知事件不能消失。

## 原因

评论是可见内容，通知是事件记录，两者生命周期不同：评论可以软删除并保留位置，通知需要保留事件以便审计。回复如果只在 Java 层检查 noteId，数据库无法防止遗漏路径写入，因此要让复合外键承担最终约束。当前单体写入量较小，通知写入放进同一事务可以避免评论成功而通知丢失。

## 原理

V5 建立 `comments` 和 `notifications`。`comments` 以 `(parent_id, note_id) → (id, note_id)` 复合外键保证回复和父评论属于同一笔记；服务层先锁定笔记和父评论，再检查可见性、状态和文本规则。评论列表用 `id ASC` 游标，删除只更新 `status=2/deleted_at`，返回固定的“该评论已删除”占位。

评论创建、点赞、关注和通知写入共享 MySQL 事务；自互动不生成自通知。Redis 键 `rl:comment:{userId}` 用 60 秒窗口限制每个用户 20 条评论。通知列表用 `id DESC` 游标，指定 id 或空数组批量更新 `read_at`，查询额外返回 `unreadCount`。

2. 执行 `node docs/dev/test-p10-comments.mjs` 得到 `PASS=17 FAIL=0`，覆盖公开/私密可见性、一级评论/回复、跨笔记父评论、HTML、500 字限制、20 条/分钟限流、游标、作者权限、软删占位、评论/回复/点赞/关注通知、指定/全部已读和数据库约束。

## 可复用结论

- 软删除内容和事件记录要分开定义生命周期：内容保留占位，通知保留事件，不用级联物理删除。
- 跨字段业务约束应同时由服务层可读校验和数据库复合外键兜底；服务层负责友好错误，数据库负责阻止遗漏路径。
- 同步通知适合当前小规模单体，但要把事务边界、失败行为和未读数查询写成可重跑证据；达到吞吐门槛后再引入 outbox，不提前增加队列复杂度。
