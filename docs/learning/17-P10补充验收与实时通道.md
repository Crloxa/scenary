# 17 · P10 补充验收与实时通道

> 触发：补齐 P10 原验收未覆盖的敏感词、实时通知、跨浏览器、键盘/读屏语义和压力基线，并首次把原生 WebSocket 接入事务提交后的通知刷新。

## 现象

P10 初版只有 HTTP 通知轮询。评论敏感词、实时到达延迟、不同浏览器的详情/通知路由、动态提示的无障碍语义和可复现并发数据没有独立证据，不能只凭主流程通过就宣称覆盖。

## 原因

这些能力跨越后端配置、事务边界、Nginx 升级头、浏览器 API 和验收环境。HTTP 主链路通过，只能证明通知最终可以查询，不能证明 WebSocket 认证、提交后推送或断线降级；单一浏览器也不能代表 Firefox/WebKit。

## 原理

WebSocket 只发送不含正文的刷新信号，客户端收到后继续通过通知 HTTP API 读取真实数据。服务端把事件监听放在 AFTER_COMMIT，因此回滚事务不会向在线用户发送假通知；首帧用 access JWT 认证，令牌不出现在 URL。前端连接失败或断开时保留 30 秒轮询和有限重连，通道故障不阻塞页面。

## 我怎么验证的

1. 通过 node docs/dev/test-p10-comments.mjs 验证配置词表命中后统一返回 40000 且不回显词项，评论限流和历史 P10 断言共 18/18 通过。
2. 通过 node docs/dev/test-p10-realtime.mjs 经 http://localhost:8081 穿过 Nginx 建立真实 WebSocket，验证首帧 JWT、READY、评论接口成功后的提交后 NOTIFICATION、非法令牌关闭和 Compose 升级配置，4/4 通过。
3. 通过 cd frontend && npm run test:e2e -- --reporter=line 在 Chromium、Firefox、WebKit 各执行详情评论与通知路由专项，并验证可访问名称和键盘焦点，6/6 通过。页面使用无后端的 mock WebSocket，真实通道由第 2 步覆盖。
4. 通过 node docs/dev/test-p10-load.mjs 执行 10 并发、约 10 秒只读请求，得到 15561 请求、错误率 0、吞吐 1555.01 req/s、p50/p95/p99 5.75/11.49/16.64 ms，结束后健康检查通过；docker stats --no-stream 记录 backend 411.3MiB、frontend 13.96MiB 的事后快照。

## 可复用结论

- 实时通道应是 HTTP 可靠读取链路的增强信号，不应把完整通知正文或未确认状态只放在 WebSocket 中。
- 事务事件必须在提交后发布；测试必须把写接口返回成功作为先决条件，再等待推送，才能验证提交边界。
- 跨浏览器和无障碍专项要把浏览器矩阵、mock 边界和真实通道黑盒分别记录，避免“测试通过”掩盖未覆盖环境。
- 压测脚本应固定并发、时长、请求集合和退出条件；错误率非零或压测后健康检查失败时返回非零退出码。
