## 1. 项目定位与 MVP 边界

Scenary 是一个"小红书式"的图文社区 MVP：用户注册登录 → 在双列瀑布流主页浏览别人的风景笔记卡片 → 自己也能发图文笔记 → 在个人中心管理资料和作品。

范围铁律（防止范围膨胀）：

| 模块 | MVP 做到什么程度 |
|---|---|
| 认证 | 用户名+密码注册/登录/登出/刷新令牌。不做邮箱验证、短信、三方登录、找回密码（记 TODO） |
| 主页 | 双列瀑布流，按发布时间倒序全站公开笔记，游标分页无限滚动。不做任何个性化推荐 |
| 发布 | 标题(≤64字)+正文(≤2000字)+1~9 张图+可选地点名文字。纯客户端裁剪预览，不做服务端拼贴/滤镜 |
| 个人中心 | 查看/编辑昵称签名头像，展示本人笔记九宫格与他人主页只读版 |
| 笔记详情 | 大图+文字+作者信息浏览闭环（瀑布流卡片的落地点） |

**不做的理由都要能一句话说清**：推荐算法（产品冷启动无数据）、评论（社交重交互，留到 P10）、私信、后台管理（运维直接 SQL）、搜索（MySQL LIKE 起步即可，二期再上 ES）。点赞/收藏/关注已在 P9 以关系表落地，`notes.like_count` 仍只作为历史预留字段不手工维护。

**为思绪.txt 预留的三个缝**（现在不实现，但设计已对齐）：

1. `notes.place_name` 文本字段 → 二期加 `lat/lng` 列的 migration 即可接地图；
2. RabbitMQ 的 `media.process` 消费者链路 → 二期在缩略图 consumer 后追加"人物检测 consumer"，就是 AI 安全门；
3. `media` 表保留原始 `object_key` 且缩略图强制重编码剥元数据 → 二期 EXIF GPS 提取只读不入库，隐私模型已经正确。

## 2. 总体架构

### 2.1 运行拓扑（6 个容器）

```
                 浏览器
                   │ :8081
        ┌──────────▼──────────┐
        │  nginx (frontend)   │  静态资源 + /api 反向代理 (同源,免CORS)
        └──────────┬──────────┘
                   │ /api
        ┌──────────▼──────────┐
        │ scenary-backend     │ Spring Boot 单体 (jar)
        │  ├─ Auth/JWT        │
        │  ├─ Note/Feed/User  │──► MySQL 8.4   (InnoDB, Flyway 管 DDL)
        │  ├─ Redis 读写      │◄─► Redis 7     (令牌白名单/限流/首页缓存)
        │  └─ MinIO SDK       │◄─► MinIO       (原图+缩略图对象存储)
        │      └─ 发布消息    │
        │            ▼        │
        │  RabbitMQ           │ media.uploaded ► 缩略图消费者(manual ack)
        │    └─ DLQ 兜底      │        └────► 回写 media.status/thumb_url
        └─────────────────────┘
```

- **单体优先**：MVP 一个 Spring Boot 进程装下全部业务，按包拆模块（auth/user/media/note/feed），不上微服务。模块间只准走 Service 接口调用，未来要拆的时候沿包边界切。
- **前端静态化**：Vue 3 构建出的纯静态文件由 nginx 托管；所有 API 走 `/api` 同源反代，开发环境用 Vite proxy 达成同样效果 —— 全程无 CORS 问题。
- **异步解耦**：上传接口只做"存原图+建记录+发消息"就返回；生成缩略图的耗时活由 MQ 消费者慢慢干，前端轮询状态。这是本项目唯一一处异步链路，也是思绪二期 AI 审核门的插槽。

### 2.2 核心时序（发布一篇笔记）

```
浏览器                     Backend                        MinIO/RabbitMQ
  │ ①POST /media/images(9张)  │                               │
  │──────────────────────────►│ 每张: 流式写 MinIO 原图         │
  │                           │ 建 media 行(status=PROCESSING) │
  │                           │ 发 media.uploaded 消息 ───────►│
  │◄──[{mediaId,url,status}]──│ 立即返回,不等缩略图             │
  │ ②轮询 GET /media/{id} ... │        ...消费者生成缩略图...    │

  │ ③POST /notes{mediaIds[]}  │ 校验9张全DONE→事务:插note+回填  │
  │                           │ 清除首页缓存                    │
  │◄────────noteId────────────│                               │
  │ ④GET /feed?cursor=…       │ 首页缓存(Redis 5min)或DB游标查询 │
```

| 前端测试（Vitest + @vue/test-utils + jsdom + Playwright） | P8 前端回归与后续浏览器剧本 | 仅 frontend 的 devDependencies、tests/e2e 和 CI；业务源码不感知测试框架 | 低；仅增加开发期依赖与浏览器缓存 |

### 4.1 分包风格：按业务模块切，而不是按技术层切

很多人熟悉的分包是"分层制"（package-by-layer）：所有控制器挤在一个 `controller/` 包、所有 Service 挤在一个 `service/` 包。本项目采用**模块制**（package-by-module）：以上面的 `auth/`、`user/`、`note/` 为一级包，每个业务模块是一个自包含的纵切面。

同一个功能的文件，两种摆法的对照：

```
分层制(旧理解)                     模块制(本项目)
com.scenary                       com.scenary
├── controller/                   ├── auth/
│   ├── AuthController            │   ├── AuthController
│   ├── UserController            │   ├── AuthService        ← 该业务的层都住在一起
│   └── NoteController            │   ├── JwtUtil / dto …
├── service/                      ├── user/
│   ├── AuthService               │   ├── UserController
│   ├── UserService               │   ├── UserService
│   └── NoteService               │   ├── UserEntity / UserMapper(+XML)
├── mapper/                       ├── note/
│   ├── UserMapper                │   ├── NoteController / NoteService
│   └── NoteMapper                │   ├── NoteEntity / MediaEntity*
└── entity/                       └── feed/ …
    ├── User / Note
```

直接回答两个常见疑问：

1. **模块内部还有没有 controller/service/dao 这些角色？** —— 角色一个不少，只是不再存在全局唯一的 `controller/` 目录；它们以**类名后缀**体现（`*Controller`/`*Service`/`*Mapper`），住在各自业务包里。数据库访问层即 Mapper（MyBatis 语系里 DAO≈Mapper）。单个模块文件数 ≤15 时建议包内平铺靠后缀区分；超过 15 再建 `dto/`、`mapper/` 子包，规则写死避免争论。
2. **和分层制行为有什么不同？** —— 代码总量一样，变的是**依赖方向的物理表达**：
   - 分层制下横向任意 Service 互调、纵向 controller 直接翻 mapper 都很方便，久了形成蜘蛛网；
   - 模块制下约定一条单向规则（下一行），跨模块只能走对方 Service 门面，Mapper/Entity 是模块私有实现细节；
   - 附带三个红利：改一个功能只动一个包（内聚）；某天拆微服务时，包边界≈服务边界，搬家不重排；配合 ArchUnit 几行测试即可机器化守护依赖方向（进阶可选项，MVP 不强制）。

   代价也说清楚：初次找文件要先想"这是哪个业务"而不是"这是哪一层"；跨模块的字段复用必须显式提升到 common 或对方 VO，不能随手 import 别人的 Entity —— 这恰好逼你理清契约，短期麻烦长期受益。

**依赖方向铁律**：`其它模块 Controller → 本模块 Service ✅`；`其它模块 Service → 本模块 Service ✅`（仅限门面方法）；**`任何跨包 Mapper / Entity 直接引用 ❌`**；公共设施一律放 `common/`。

## 5. 四个核心设计决策

### 5.1 认证：JWT 双令牌 + Redis 白名单

- 注册/登录成功签发两个令牌：**access token**（JWT，2 小时，无状态）+ **refresh token**（JWT，30 天，jti 存入 Redis 白名单 `auth:refresh:{userId}:{jti}`）。
- 拦截器（`AuthInterceptor`）校验 access token，通过后把 userId 放进 ThreadLocal 的 `UserContext`，请求结束清理。
- **登出**：删除该用户全部 refresh 白名单键 + 把当前 access token 的 jti 加入黑名单 set（TTL=access 剩余寿命）。双保险。
- **刷新**：`POST /auth/refresh` 带 refresh token → 校验签名且 jti 在白名单 → 删除旧 jti、签发全新对（旋转），防重放。
- 安全底线：BCrypt(cost 10) 存密码；注册 IP 限流 20 次/小时、单账号登录连错 5 次锁 15 分钟（Redis 计数器）；JWT 密钥走 env，长度 ≥32 字符。

面试点提示：为什么 access 短 refresh 长？——失窃窗口小+体验好；为什么 refresh 要入库（Redis）？——有状态才能主动吊销。

### 5.2 上传管线：RabbitMQ 异步缩略图（含死信）

```
POST /api/v1/media/images (multipart, ≤9张, 单张≤10MB，jpeg/png/gif)
 后端逐张: 校验magic number(mime) → MinIO putObject orig/{yyyyMM}/{uuid}.ext
          → insert media(status=0 PROCESSING) → rabbitTemplate.send("media.uploaded", {mediaId})
ThumbnailConsumer(concurrency=2, prefetch=1, MANUAL ack):
 拉取原图流 → Thumbnailator 生成 ≤800px JPEG q0.8(重编码天然剥离EXIF) → putObject thumb/...
 → UPDATE media SET status=1, thumb_url, width, height → channel.basicAck
异常: try两次本地catch失败 → 先写 status=2/失败原因/时间 → basicNack(requeue=false) → x-dead-letter-exchange → media.dlq(留档人工重放)
前端轮询 GET /media/{id} 直到 status∈{1,2}; 发布笔记时校验所选 media 必须 status=1
```

要点：**manual ack + requeue:false + DLX** 三件套保证不丢不循环风暴；消费者幂等天然成立（重复消费只是覆盖同一 thumb 键）。当前不接收 WebP，避免无解码器时先存原图再异步失败；若未来引入 WebP 解码器，先更新依赖冻结线与 API 契约。

### 5.3 Feed： Newest-first 游标分页 + 两级缓存

- 语义：全站公开笔记按 `id DESC`（自增主键≈时间序）。SQL 固定：
  `SELECT … FROM notes WHERE visibility=1 AND id < #{cursor} ORDER BY id DESC LIMIT #{limit}`，首参 cursor 默认无穷大。
- 缓存两级：① 默认第 1 页（10 条）结果整页 JSON 存 Redis（key=`feed:first:v1:{version}`，TTL 300s）；发布或删除事务方法返回后由 Controller 推进 `feed:first:v1:version`，旧查询即使迟到写回也只落到旧版本键，避免把未提交快照暴露为当前页。命中时仅用首页覆盖索引核对笔记 ID 序列，失配即重建；自定义 `limit` 不复用 L1。② 卡片单条 VO 缓存 `note:card:{id}` TTL 1h，翻页时命中则跳过 DB 回表。
- 为什么不用关注流推模式：P9 虽已建立关注关系，但当前产品仍按全站最新 Feed 展示，关注流和推荐排序留到后续阶段；为什么不用 zset 时间线：当前读多写少+量小，两级字符串缓存足够，后续做推荐算法时把 `FeedService.listFeed()` 换成策略接口实现即可（预留 `FeedProvider` 接口位）。

### 5.4 对象存储与隐私

- 桶 `scenary-media`，MVP 设 public-read 直链访问（生产化增强项：改私有桶+预签名 URL，文档备注即可）。
- 路径布局：`orig/{yyyyMM}/{uuid}.{ext}`、`thumb/{yyyyMM}/{uuid}_t.jpg`、`avatar/{userId}/{uuid}.jpg`。
- **上传走后端代理**而非浏览器直传 MinIO（预签名直传）：MVP 图≤10MB×9，代理链路简单可控、校验集中；直传列入性能优化备忘。
- 隐私默认值：前端展示只用缩略图/压缩后的 URL；原图 object_key 只存在库里（个人中心下载原图用）；缩略图重编码保证不含 GPS 等 EXIF。这与 Pixelfed 的做法一致（其 config/image.php strip=true 的同款策略），也是思绪.txt 地点标注合规叙事的基础。

### 6.1 P9 社交关系表（Flyway V4__social_relations.sql）

P9 新增点赞、收藏、关注三张关系表。关系表的唯一键是幂等与并发去重的最终保障；详情、Feed 和主页返回的计数均由关系表实时聚合，不依赖 `notes.like_count` 这个 MVP 预留字段的手工维护。

```sql
CREATE TABLE note_likes (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  note_id BIGINT UNSIGNED NOT NULL,
  user_id BIGINT UNSIGNED NOT NULL,
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_note_like_user (note_id, user_id),
  KEY idx_like_user_created (user_id, created_at),
  CONSTRAINT fk_like_note FOREIGN KEY (note_id) REFERENCES notes(id),
  CONSTRAINT fk_like_user FOREIGN KEY (user_id) REFERENCES users(id)
) ENGINE=InnoDB COMMENT='笔记点赞关系';

CREATE TABLE note_bookmarks (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  note_id BIGINT UNSIGNED NOT NULL,
  user_id BIGINT UNSIGNED NOT NULL,
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_note_bookmark_user (note_id, user_id),
  KEY idx_bookmark_user_created (user_id, created_at),
  CONSTRAINT fk_bookmark_note FOREIGN KEY (note_id) REFERENCES notes(id),
  CONSTRAINT fk_bookmark_user FOREIGN KEY (user_id) REFERENCES users(id)
) ENGINE=InnoDB COMMENT='笔记收藏关系';

CREATE TABLE follows (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  follower_id BIGINT UNSIGNED NOT NULL,
  following_id BIGINT UNSIGNED NOT NULL,
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_follow_pair (follower_id, following_id),
  KEY idx_following_created (following_id, created_at),
  KEY idx_follower_created (follower_id, created_at),
  CONSTRAINT fk_follow_follower FOREIGN KEY (follower_id) REFERENCES users(id),
  CONSTRAINT fk_follow_following FOREIGN KEY (following_id) REFERENCES users(id),
  CONSTRAINT ck_no_self_follow CHECK (follower_id <> following_id)
) ENGINE=InnoDB COMMENT='用户关注关系';
```

删除笔记后禁止新社交关系，历史关系保留以便审计；收藏列表只返回当前仍公开且未删除的笔记。P9 不新增第三方依赖、消息队列或缓存键。

设计说明：

- **MVP 就三张业务表，P9 以 V4 增加三张关系表**。refresh token 在 Redis 不建表；评论、通知仍留到 P10。
- 游标分页吃两个索引：全站 feed 走 `idx_feed_cursor`，个人主页网格走 `idx_user_visibility_id`。
- 软删用 `visibility=2 + deleted_at` 而非物理删，MinIO 文件不删（复原友好、省事），空间治理属于远期运维任务。
- `place_name` 先收文本；二期加 `lat DECIMAL(10,6), lng DECIMAL(10,6)` 列即可平滑升级到地图，不需要动已有行。
- 媒体与笔记用 `media.note_id` 外键表达一对多，不再建关联表——"先传图后发布"的两段式里，未绑定状态的 media 天然存在（note_id 为空）。

ER 关系：

```
users 1 ──── N notes 1 ──── N media (media.note_id 绑定)
  └───────── N media (先上传未绑定的游离媒体, user_id 归属)
users 1 ──── N note_likes / note_bookmarks（user_id）
notes 1 ──── N note_likes / note_bookmarks（note_id）
users 1 ──── N follows（follower_id / following_id）
Redis(非表): auth:refresh:* / auth:blacklist / rl:* 限流计数 / feed:first:v1:{version} + feed:first:v1:version / note:card:{id}
```

## 8. 工程约定

- Git：主干 `main` 单分支流（个人项目），提交粒度=每个 Phase 一串原子 commit，格式 `feat(note): 发布笔记接口`。
- 配置：一切环境相关配置走 `.env` + compose `environment:`，仓库绝不出现真实密码；JWT 密钥/OBJ 密钥用 openssl rand 生成。
- 日志：logback 默认级别 INFO，`logging.pattern` 带 traceId（MDC 过滤器一行实现）；异步消费者单独 logger 方便排障。
- 时区：JVM `-Duser.timezone=Asia/Shanghai`，MySQL 驱动连接参数 `connectionTimeZone=Asia/Shanghai`；API 输出时间一律 epoch millis（见 02 文档约定）。
- 命名：Java 驼峰、DB 蛇形、JSON 字段驼峰；DTO 按 `*Request/*VO` 后缀。
- 测试基调：以 `docs/dev/smoke-backend.http` 冒烟脚本为最低标准（03-P3）；Service 层关键分支（登录锁、发布校验、DLQ 重试）鼓励 Junit5 单测但不强制凑覆盖率。
- 事件扩展约定：MQ 复用同一个 topic exchange `media.event`，routing key 以 `<域>.<动作>` 命名（`media.uploaded` 已占用）；未来任何新异步链路（`note.published`、AI 审核门、视频转码）一律**新增 routing key + 新队列绑定**，禁止复用既有队列语义。
- 密钥/口令格式：一律 `openssl rand -hex`（纯十六进制），杜绝 base64 的 `+/=` 在 shell 与 YAML 里的转义歧义。
