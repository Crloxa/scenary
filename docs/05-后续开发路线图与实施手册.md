# Scenary 05 · 后续开发路线图与实施手册

> 版本：v1.1 · 2026-09-04
> 目标：在 P8 产品与工程补强完成后，按可控增量继续演进 Scenary。
> 前置门槛：P8 必须有完整证据报告；若 P8 的 P0 问题仍未关闭，后续阶段只能做研究文档，不得进入开发。

## 1. 路线图总览

```text
P8 质量恢复与产品重构 ✅
 ├─ P9 社交最小闭环：点赞 / 收藏 / 关注 ✅
 ├─ P10 评论与通知：评论、回复、站内通知
 ├─ P11 搜索与发现：关键词、标签、排序、推荐接口
 ├─ P12 二期 A：视频上传 / 转码 + 地点坐标
 ├─ P13 内容安全：审核状态、人物检测插槽、人工处置
 └─ P14 规模化运维：私有对象、CDN、异步任务平台、水平扩展
```

阶段不是按日历自动推进，而是按出口条件推进。每个阶段包含：产品目标、数据/API 变化、前端工作、后端工作、运维工作、测试证据和回滚策略。

## 2. 共同开发规则

### 2.1 立项前五问

任何新功能开工前，必须在阶段文档或 ADR 中回答：

1. 用户在什么页面、因为什么动机使用它？
2. 新状态如何显示，失败后如何恢复，删除后如何撤销？
3. 是否需要新表/字段/队列/依赖？迁移和回滚是什么？
4. 哪些接口是公开的，哪些需要登录，资源所有权如何判断？
5. 最小可验证场景是什么，哪条命令或浏览器剧本能证明完成？

### 2.2 API 与数据演进

- API 继续使用 `/api/v1`；破坏性变更必须新增版本或提供兼容期。
- 新表使用 `Vn__description.sql`，禁止修改已应用 migration。
- 所有写接口优先设计幂等键、审计字段和软删语义；所有列表接口必须定义分页、排序和可见性。
- 跨模块只能调用 Service 门面；事件只新增 routing key 和队列，不复用已有队列语义。

### 2.3 通用验收门禁

每个阶段至少提交：

- API 契约更新与正反例。
- Flyway migration 验证（空库、已有数据、回滚/前向兼容说明）。
- 后端单测 + 集成/黑盒测试。
- 前端组件测试 + 一条浏览器主流程。
- 性能基线（样本量、p95、资源消耗）和安全边界。
- `docs/evidence/YYYY-MM-DD-阶段主题.md`，并同步 03 Checklist、HANDOVER、CHANGELOG。

## 3. P9 · 社交最小闭环

### 3.1 目标与边界

让用户对公开笔记产生最小反馈：点赞、取消点赞、收藏、取消收藏、关注/取消关注。P9 不做推荐算法、不做私信、不做评论，避免一次引入过多关系和通知。

### 3.2 数据模型建议

新增 migration（名称以实际落盘为准）：

```sql
CREATE TABLE note_likes (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  note_id BIGINT UNSIGNED NOT NULL,
  user_id BIGINT UNSIGNED NOT NULL,
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_note_user (note_id, user_id),
  KEY idx_user_created (user_id, created_at),
  CONSTRAINT fk_like_note FOREIGN KEY (note_id) REFERENCES notes(id),
  CONSTRAINT fk_like_user FOREIGN KEY (user_id) REFERENCES users(id)
) ENGINE=InnoDB;

CREATE TABLE note_bookmarks (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  note_id BIGINT UNSIGNED NOT NULL,
  user_id BIGINT UNSIGNED NOT NULL,
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_bookmark_note_user (note_id, user_id),
  KEY idx_bookmark_user_created (user_id, created_at)
) ENGINE=InnoDB;

CREATE TABLE follows (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  follower_id BIGINT UNSIGNED NOT NULL,
  following_id BIGINT UNSIGNED NOT NULL,
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_follow_pair (follower_id, following_id),
  CONSTRAINT ck_no_self_follow CHECK (follower_id <> following_id)
) ENGINE=InnoDB;
```

计数不要只依赖 `notes.like_count` 的手工更新：写入关系表与计数更新必须在同一事务，或改为异步计数并接受明确的最终一致性。删除/私密笔记必须阻止新点赞，历史关系按产品决策保留或清理。

### 3.3 API 草案

| 方法 | 路径 | 语义 |
|---|---|---|
| PUT/DELETE | `/notes/{id}/like` | 幂等点赞/取消点赞 |
| PUT/DELETE | `/notes/{id}/bookmark` | 幂等收藏/取消收藏 |
| PUT/DELETE | `/users/{id}/follow` | 幂等关注/取消关注 |
| GET | `/users/me/bookmarks` | 当前用户收藏列表，游标分页 |

响应统一返回 `liked/bookmarked/following` 和计数，避免前端再发三次请求拼状态。公开详情匿名时不返回用户私有收藏状态。

### 3.4 验收

- 两次相同 PUT 不增加计数，两次 DELETE 不报错。
- 不能给私密/已删除笔记点赞；不能关注自己；被禁用用户关系不可创建。
- 并发 20 次点赞最终只有一条关系，计数与关系表一致。
- 首页和详情页登录/匿名视图差异明确，刷新后状态一致。

## 4. P10 · 评论与通知

### 4.1 目标

提供一级评论和对评论的回复，并把点赞、关注、评论统一成站内通知。P10 不做实时 WebSocket，先用分页轮询，降低部署复杂度。

### 4.2 数据模型

`comments` 至少包含 `id/note_id/user_id/parent_id/content/status/created_at/updated_at/deleted_at`；`parent_id` 只允许指向同一笔记的评论。`notifications` 至少包含 `id/recipient_id/actor_id/type/note_id/comment_id/read_at/created_at`，所有关联字段允许为空以兼容不同事件。

内容限制：一级评论 500 字，回复 300 字；服务端做长度、敏感字符和频率限制，前端只做体验校验。

### 4.3 API 与交互

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/notes/{id}/comments` | 游标分页，按时间正序或热度排序需固定契约 |
| POST | `/notes/{id}/comments` | 创建一级评论或带 parentId 回复 |
| DELETE | `/comments/{id}` | 作者或管理员软删 |
| GET | `/notifications` | 当前用户通知分页 |
| POST | `/notifications/read` | 批量标记已读 |

前端详情页评论区必须有：加载更多、提交中、失败重试、删除确认、空态、被删除占位、未登录引导。通知入口显示未读数，但不能因轮询失败阻塞主页面。

### 4.4 异步事件

在 `media.event` 之外新增 `social.event` exchange 或按 01 文档登记新的 routing key；推荐使用 outbox 表记录评论/点赞事件，再由消费者创建通知，避免主事务因通知失败回滚。

## 5. P11 · 搜索与发现

### 5.1 分阶段方案

先用 MySQL 前缀/全文索引完成可用搜索，再评估 Elasticsearch。不要在没有真实查询样本和性能数据前直接引入 ES。

第一阶段支持：标题、正文、地点名、作者昵称；过滤公开内容、已删除内容和禁用用户；结果按相关性再按时间稳定排序。

### 5.2 API 草案

`GET /search/notes?q=&cursor=&limit=&sort=recent`，响应沿用 `NoteCardVO`，增加 `highlight` 可选字段。`q` 至少 2 个字符，最大 64 个字符；空查询返回 40000，不返回全站数据。

### 5.3 索引与缓存

- P11 初版使用 MySQL FULLTEXT 或受控 LIKE，并新增合适索引；记录查询 p95 和慢查询样本。
- 若迁移 ES，新增 `search` 模块与 `note.published/note.updated/note.deleted` 事件，不让 Controller 直接写索引。
- 搜索结果缓存必须包含 query、sort、cursor、可见性视角，不能复用首页 L1。

### 5.4 验收

覆盖中文、英文、特殊字符、空格、大小写、已删除和私密内容；结果无越权、分页无重复；索引延迟和重建脚本可测、可回滚。

## 6. P12 · 二期 A：视频上传与地点标注

### 6.1 视频上传

分两步做：

1. **基础链路**：扩展 media 类型、大小和状态机，上传后进入 `video.transcode` 队列，生成封面和多码率 MP4；前端显示转码进度与失败重试。
2. **体验优化**：大文件改为分片/预签名直传，服务端只负责创建上传会话、合并和校验；引入断点续传与过期会话清理。

新增状态至少区分 `UPLOADING/PROCESSING/READY/FAILED/EXPIRED`，不能复用图片的三态。视频发布前必须确保封面和播放地址就绪。

安全限制：扩展名不可信，必须检查容器格式/魔数；限制时长、分辨率、总大小和并发转码数；原始视频默认私有，播放地址使用短时签名或受控反代。

### 6.2 地点标注

扩展 notes：`place_name` 保留，新增 `lat/lng/place_source/place_precision`。来源分为用户手填、EXIF、地图选择；EXIF 只在服务端读取，不把原始 GPS 写回公开对象或响应。

API 可增加 `GET /places/reverse-geocode`，但必须有供应商超时、配额、缓存和隐私说明。地图展示优先使用 Leaflet 等轻量方案，新增依赖需走 01 §3.1 登记。

### 6.3 验收

- 图片和视频队列互不阻塞，单一毒消息不会拖垮另一条链路。
- 转码失败可观测、可重试、可进入 DLQ；已发布内容不会暴露原始文件。
- EXIF GPS 测试夹具确认：公开响应不带 GPS；用户明确选择分享地点时才显示坐标。
- 大文件、断点、刷新、离开页面和重复提交均有浏览器回归。

## 7. P13 · 内容安全与审核

### 7.1 状态模型

将“可见性”和“审核状态”分开：`visibility` 表达公开/私密/删除，`moderation_status` 表达 pending/approved/rejected/manual_review。审核拒绝不能通过把 visibility 改成 2 混过去。

### 7.2 处理链路

```text
media uploaded
  -> thumbnail / metadata strip
  -> moderation.pending
  -> rules + optional person detector
  -> approved | rejected | manual_review
  -> note publish visibility gate
```

规则检测先做文件类型、尺寸、EXIF、哈希和基础敏感词；人物检测或第三方 AI 仅作为可插拔 consumer，必须有超时、重试、成本上限和人工兜底。

### 7.3 管理与审计

没有管理员角色前，不开放公网管理接口；先提供受保护的内部脚本/只读报表。每次审核决定保存 actor、规则版本、输入摘要、时间和原因，禁止保存不必要的原图副本。

## 8. P14 · 规模化运维

### 8.1 对象存储与 CDN

私有桶 + 短时预签名 URL 是默认目标；缩略图可通过 CDN 缓存，原图按权限签名。迁移必须支持双读（旧直链/新签名）和批量回填，完成后再关闭旧路径。

### 8.2 服务拆分条件

只有出现明确瓶颈才拆分：

- API p95 在已优化查询后仍超目标；
- 转码/审核任务占满 Web 进程资源；
- 团队需要独立发布和扩容；
- 单体模块边界和事件契约已有测试保护。

拆分顺序建议：worker（媒体/审核）→ search → notification，最后才考虑 auth/user/note/feed。状态继续外置到 MySQL/Redis/对象存储，拆分前先补契约测试。

### 8.3 可观测性目标

最小指标：HTTP 请求量/错误率/p50/p95、登录失败率、上传成功率、媒体处理延迟、DLQ 深度、缓存命中率、数据库连接池、对象存储错误率。日志必须结构化并带 traceId；告警阈值写入 ops 文档并可通过脚本验证。

| 顺序 | 阶段 | 进入条件 | 退出证据 |

| 1 | P8 | 当前 MVP 复验完成 | P8 证据、前后端回归、P0 清零 |
